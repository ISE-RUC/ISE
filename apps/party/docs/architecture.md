# 党团事务模块设计说明

## 1. 文档目的

本文档用于沉淀 ISE 项目中党团事务模块的业务理解、模块边界、技术选型、分层架构和开发路线，作为后续代码实现、接口设计、测试设计和验收的内部依据。

本文档基于以下内容整理：

- 项目现有代码骨架
- SRS 文档中党团事务模块相关要求
- 当前 Django 项目整体结构与约束

## 2. 需求来源与约束

### 2.1 SRS 中与党团事务相关的核心要求

根据提取后的需求文档，党团事务模块属于 `P0` 级核心模块，关键要求如下：

1. 需要固化入党、入团全流程，并以状态机方式管理。
2. 流程是线性的，不允许越级跳转。
3. 需要支持学生查看个人进度追踪。
4. 需要根据标准时间线自动触发关键节点提醒。
5. 需要支持材料提交与节点办理。
6. 需要支持老师审批、批量审批和审批撤回。
7. 需要支持 RBAC 四级权限模型。
8. 涉及新增、修改、审批的操作需要写入审计日志。
9. 系统需要同时兼顾移动端学生视图和 PC 端管理视图。
10. 最终数据库环境需要兼容 Kingbase。

### 2.2 现有项目中的已知约束

当前项目已经具备以下基础条件：

- 后端框架已经使用 Django。
- 用户模型已经定义四级角色。
- 已有基础权限 mixin。
- 已有审计日志模型与中间件雏形。
- `apps/party` 中已有初始状态模型骨架。

当前项目仍存在以下缺口：

- 党团事务模块只有极简模型，缺少完整流程建模。
- 当前视图只有占位页，没有实际业务流程。
- 审计中间件尚未接入 `MIDDLEWARE`。
- 管理端和学生端页面尚未分离。
- 现有模型还不足以支持审批、材料、提醒和撤回逻辑。

## 3. 模块目标

党团事务模块的目标不是单纯展示一个“当前状态”，而是实现一套可追踪、可审批、可提醒、可审计的业务流程系统。

具体目标如下：

1. 统一管理学生党团发展档案。
2. 对标准流程节点进行系统化表达。
3. 支持学生在当前节点提交材料。
4. 支持老师对节点进行审核、通过、驳回和撤回。
5. 支持自动生成待办与提醒。
6. 支持学生端时间轴式查看流程进度。
7. 支持管理端审批工作台和批量处理。
8. 保证流程不可跳级、数据可追溯、权限边界清晰。

## 4. 推荐总体架构

建议将党团事务模块按“数据层 + 业务服务层 + 视图层 + 文档层”组织。

### 4.1 数据层

负责表达流程主表、节点实例、材料提交、审批任务、提醒任务等持久化数据。

### 4.2 业务服务层

负责封装复杂业务规则，避免把流程跳转、审批和提醒逻辑直接写在视图中。

### 4.3 视图层

负责区分学生端与管理端页面，控制输入输出、权限检查和页面渲染。

### 4.4 文档层

负责存放该模块的需求说明、字段说明、接口说明和开发约定。

## 5. 数据模型设计建议

当前 `apps/party/models.py` 中只有：

- `PartyMemberStatus`
- `PartyProgressRecord`

这两个模型只能算初始骨架，不足以表达完整业务。建议扩展为以下核心实体。

### 5.1 党团发展主表

建议保留并升级现有 `PartyMemberStatus`，使其成为学生党团流程主档案。

建议职责：

- 绑定一个学生
- 标记是入党流程还是入团流程
- 标记当前所处阶段
- 记录进入当前阶段时间
- 记录预计下一节点时间
- 记录流程锁定状态
- 存放管理员备注

建议字段：

- `user`
- `track_type`
- `current_stage`
- `status_since`
- `expected_next_date`
- `is_locked`
- `notes`
- `created_by`
- `updated_at`

### 5.2 流程节点定义表

建议新增节点定义模型，用于描述标准流程，而不是把规则硬编码在视图或模板中。

建议职责：

- 定义节点代码和名称
- 定义节点顺序
- 定义最短停留时长
- 定义是否要求培训合格
- 定义需要提交的材料类型
- 定义该节点由哪个角色审批

建议字段：

- `code`
- `name`
- `order`
- `track_type`
- `min_duration_days`
- `requires_training`
- `is_active`

### 5.3 节点实例表

建议为每个学生的每个流程节点生成实例记录，而不是只在完成后写一条附件记录。

建议职责：

- 标记某学生在某节点上的办理状态
- 标记开始时间、到期时间、完成时间
- 标记当前审批状态
- 支持挂接材料和审批动作

建议字段：

- `member`
- `stage_code`
- `status`
- `started_at`
- `due_at`
- `completed_at`
- `approval_status`
- `remark`

### 5.4 材料类型定义表

建议将“需要提交什么材料”单独建模。

常见材料类型包括：

- 入党申请书
- 思想汇报
- 培训证明
- 支部意见
- 个人总结
- 其他附件

建议字段：

- `code`
- `name`
- `description`
- `allowed_extensions`
- `max_size_mb`
- `is_required`

### 5.5 材料提交表

建议新增材料提交模型，用于保存学生实际上传的材料。

建议职责：

- 保存材料文件
- 记录谁提交、何时提交
- 记录审核状态
- 记录驳回意见
- 支持多次提交和版本演进

建议字段：

- `stage_instance`
- `material_type`
- `file`
- `submitted_by`
- `submitted_at`
- `review_status`
- `reviewed_by`
- `reviewed_at`
- `review_comment`
- `version`

### 5.6 审批任务表

党团事务需要一个明确的审批任务实体，而不是只在状态字段上直接覆盖。

建议职责：

- 标识当前待哪个角色审批
- 支持通过、驳回、撤回、重审
- 记录审批链条
- 为工作台提供待办列表

建议字段：

- `stage_instance`
- `assignee`
- `assignee_role`
- `status`
- `created_at`
- `processed_at`
- `can_withdraw_until`
- `comment`

### 5.7 审批动作日志表

建议新增审批动作记录表，用于保留每次审批的完整历史。

建议字段：

- `task`
- `operator`
- `action`
- `comment`
- `created_at`

### 5.8 提醒任务表

提醒逻辑不能完全依赖页面实时计算，需要有任务记录以保证稳定性和可追踪性。

建议职责：

- 记录提醒类型
- 记录提醒对象
- 记录应发送时间
- 记录是否发送成功
- 支持站内提醒、邮件提醒等扩展

建议字段：

- `member`
- `stage_instance`
- `reminder_type`
- `scheduled_at`
- `sent_at`
- `status`
- `channel`

## 6. 业务流程设计

### 6.1 状态机设计

根据 SRS，流程必须严格线性，不可越级。建议先实现如下基础链路：

1. 入党申请人
2. 积极分子
3. 发展对象
4. 预备党员
5. 正式党员

后续如需支持入团流程，可在同一体系下增加 `track_type=league` 并定义另一套节点。

### 6.2 关键业务规则

必须明确固化以下规则：

1. 节点只能从前一节点流转到后一节点。
2. 未满足最短时长前不得进入下一节点。
3. 未满足材料齐备前不得提交审批。
4. 审批未通过时应回退为补材料或驳回状态。
5. 审批通过后由系统自动生成下一节点实例。
6. 需要支持老师在限定时效内撤回审批。
7. 需要记录每一次审批和撤回动作。

### 6.3 学生端业务流程

学生端应支持：

1. 查看当前所处节点
2. 查看整个流程时间轴
3. 查看当前节点所需材料
4. 上传当前节点材料
5. 查看提醒、截止时间和待办事项
6. 查看历史节点和审批意见

### 6.4 管理端业务流程

管理端应支持：

1. 查看全部学生党团状态
2. 按阶段、年级、专业、角色筛选
3. 查看待审批任务
4. 批量审批
5. 单项驳回或通过
6. 查看学生详情抽屉
7. 在时效内撤回审批
8. 批量初始化或导入流程数据

## 7. 页面架构建议

### 7.1 学生端页面

建议至少包括以下页面：

- `party/index/`：党团事务首页
- `party/timeline/`：流程时间轴页
- `party/materials/`：材料提交页
- `party/reminders/`：待办与提醒页
- `party/history/`：历史办理记录页

学生端设计重点：

- 移动端优先
- 时间轴可视化
- 当前节点高亮
- 倒计时提醒突出展示

### 7.2 管理端页面

建议至少包括以下页面：

- `party/admin/dashboard/`：总览面板
- `party/admin/members/`：成员列表
- `party/admin/approvals/`：审批工作台
- `party/admin/member/<id>/`：成员详情页
- `party/admin/import/`：批量导入页
- `party/admin/rules/`：流程规则配置页

管理端设计重点：

- PC 端优先
- 表格高密度展示
- 支持筛选、排序、批量操作
- 支持详情抽屉或侧栏展开

## 8. 推荐代码组织方式

当前模块目录已经存在，后续建议逐步演进为如下结构：

```text
apps/party/
  admin.py
  apps.py
  forms.py
  models.py
  selectors.py
  urls.py
  urls_admin.py
  urls_student.py
  views.py
  services/
    __init__.py
    workflow.py
    approval.py
    reminder.py
  docs/
    architecture.md
```

说明：

- `models.py`：定义持久化结构
- `forms.py`：处理表单输入与校验
- `selectors.py`：封装复杂查询
- `services/workflow.py`：处理状态流转
- `services/approval.py`：处理审批、撤回、重审
- `services/reminder.py`：处理提醒生成与发送
- `urls_student.py`：学生端路由
- `urls_admin.py`：管理端路由

注意：

当前仓库已经存在 `views.py` 文件，因此若后续要拆为 `views/` 包，需要同步调整导入路径和路由，不应直接无规划地同时保留同名模块与同名包。

## 9. 技术栈建议

## 9.1 后端

建议采用以下技术栈：

- `Django`
- `Django ORM`
- `Django Forms`
- `Class-Based Views`
- `django-filter`
- `openpyxl`

可选增强：

- `Celery + Redis`
- `Django REST Framework`

具体判断如下：

### Django

必须继续使用。原因：

- 当前仓库已经基于 Django
- SRS 明确要求使用 Django
- 当前用户、权限、模板和媒体文件都已经建立在 Django 之上

### Django ORM

建议继续使用 ORM 管理业务数据，但要避免写依赖 SQLite 特性的查询，以便后续切换至 Kingbase。

### Django Forms

适合第一阶段快速完成：

- 材料上传
- 审批意见提交
- 学生信息导入
- 条件筛选表单

### Class-Based Views

适合当前项目风格，可保持与现有代码一致。

### django-filter

适合管理端列表页面，减少筛选逻辑重复编写。

### openpyxl

用于：

- Excel 批量导入学生基础数据
- 导入或初始化党团流程数据

### Celery + Redis

如果后续要实现稳定的自动提醒和异步任务，推荐接入。

用途包括：

- 到期提醒
- 周期性节点检查
- 邮件提醒

如果部署条件受限，第一阶段可先用 Django management command 配合计划任务替代。

### Django REST Framework

当前阶段不是刚需。

如果后续管理端前端交互显著复杂、需要单页应用或要和其他终端解耦，再引入 DRF 更合适。

## 9.2 数据库

建议分两个阶段：

- 开发期：继续使用 SQLite 提升本地迭代效率
- 集成与部署期：切换到 Kingbase

开发时要提前注意：

- 避免使用 SQLite 特有行为
- 避免不兼容 SQL 写法
- 保持模型设计尽量标准化

## 9.3 前端

第一阶段建议继续使用：

- Django Template
- HTML
- CSS
- 少量原生 JavaScript

原因：

- 当前仓库已经是模板渲染型项目
- P0 阶段重点是跑通流程，不是重建前端体系
- 学生端和管理端都可以先用模板快速落地

可选增强：

- `htmx`
- `Alpine.js`

适用场景：

- 审批列表局部刷新
- 抽屉详情异步加载
- 批量操作后的页面局部更新

当前不建议立刻引入 Vue 或 React，除非项目目标已经明确要演进为完整前后端分离应用。

## 9.4 权限与安全

当前项目已有四级角色基础，可继续沿用：

- 一级角色：学院领导
- 二级角色：管理老师
- 三级角色：班团骨干
- 四级角色：普通学生

技术实现建议：

- 继续使用当前 `User.role`
- 将 `RoleRequiredMixin` 应用到具体视图
- 将审计中间件接入全局 `MIDDLEWARE`
- 在页面和接口两层同时做权限控制
- 对敏感数据做脱敏展示

安全重点：

1. 审批、删除、撤回等操作必须留痕
2. 文件上传必须校验大小和后缀
3. 学生不应看到不属于自己的审批记录
4. 低权限角色不能越权推进节点

## 12. 本阶段结论

本模块不应继续沿用“一个状态字段 + 一个附件记录表”的简化思路。

党团事务模块应按以下核心原则建设：

1. 流程规则独立于页面。
2. 审批任务独立于状态主表。
3. 材料提交独立建模。
4. 提醒机制独立建模。
5. 审计链路必须贯穿新增、修改、审批和撤回。
6. 学生端和管理端应明确分层。

从工程角度看，党团事务模块的核心不是页面，而是流程规则系统。后续实现中，视图应尽量只负责调用服务层，避免直接在视图中写状态流转逻辑。
