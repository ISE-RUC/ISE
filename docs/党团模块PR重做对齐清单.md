## 4. 与 API 统一定义的对齐结论

主仓已合并“API 统一定义”后，新增了以下基础能力：

- `config/api.py`
- `utils/response.py`
- `docs/API_GUIDE.md`
- `django-ninja` 依赖

当前党团模块结论如下：

- 党团模块现状以传统 Django 页面视图为主
- 目前尚未接入统一 `NinjaAPI` 路由体系
- 目前尚未统一使用 `success()` / `error()` 作为 API 响应封装
- 暂未发现“错误调用新 API”的问题
- 但存在“尚未按统一接口约定补齐”的问题

## 5. 党团模块需要补齐的 API 对齐点

### 5.1 新增党团 API 路由

建议为党团模块增加独立 Router，并在 `config/api.py` 中注册，例如：

- `/api/party/timeline`
- `/api/party/materials`
- `/api/party/approvals`
- `/api/party/reminders`

### 5.2 统一响应格式

新增 API 时必须统一使用：

- `utils.response.success`
- `utils.response.error`

禁止在同类接口中混用零散 `JsonResponse` 结构。

### 5.3 补 Schema 定义

建议为以下接口补请求 / 响应 Schema：

- 学生当前流程进度查询
- 材料上传与材料列表
- 当前节点提交审批
- 管理端审批任务列表
- 审批通过 / 驳回 / 撤回
- 提醒列表查询

### 5.4 权限与认证对齐

如拆分为 API，需要沿用现有页面中的权限约束：

- 学生仅可查看与操作自己的流程数据
- 管理员才可访问审批工作台、规则配置与导入导出能力
- 审批动作需要显式校验角色权限

认证方式优先遵循 `django-ninja` 当前示例所使用的会话认证方式。

### 5.5 迁移策略建议

建议采用“页面保留、接口渐进补齐”的方式推进，而不是一次性将党团模块全部重写为 API 驱动：

1. 保留现有 Django 页面交互
2. 先为关键读写动作补 API
3. 再逐步将页面中的关键提交、查询动作改为调用统一 API

这样能够在不打乱现有功能实现的前提下，对齐团队统一接口约定。

## 6. 下一步执行建议

建议将重做 PR 拆成两个阶段：

### 阶段一：重建干净 PR 范围

- 仅挑选 `apps/party/`、`templates/party/` 和必要党团文档
- 剔除所有非党团模块、运行产物和格式噪音

### 阶段二：补齐 API 统一定义接入

- 统一响应结构
- 为关键接口补 Schema、权限校验与文档说明

## 7. 当前结论

本次党团模块后续开发与重新提交 PR，必须遵守以下原则：

1. 先基于 `upstream/Dev` 最新代码开发
2. 仅提交党团模块相关改动
3. 不混入无关模块、全局样式、数据库文件、媒体文件与格式噪音
4. 后续新增接口时，逐步对齐已合并的 API 统一定义
