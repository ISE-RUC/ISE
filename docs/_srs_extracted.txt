1. 引言
1.1 编写目的
本文档旨在明确“学院学生综合服务与党团管理平台”的详细软件需求，将甲方（学院团委老师、辅导员及学生骨干代表）的业务需求转化为研发团队可执行的技术规格（含功能、非功能、业务流程等）。本文档将作为项目系统设计、代码开发、软件测试及最终项目验收的核心依据，确保开发成果与用户业务需求、预期目标保持高度一致。
1.2 读者对象
本文档的预期读者及核心用途如下：
•甲方用户代表：包括学院团委老师、辅导员及学生骨干代表，用于确认文档中描述的需求是否符合学院实际业务场景、是否匹配用户预期，为需求确认提供依据。
•开发团队：包括项目经理、前端工程师、后端工程师、数据库管理员，用于指导系统架构设计、数据库设计、接口开发及代码编写，确保开发工作贴合需求规范。
•测试团队：QA工程师，用于基于文档中的需求定义，编写测试用例、制定测试计划，明确测试范围及验收标准，保障软件质量。
•其他相关人员：包括学院分管学生工作的领导、项目监理人员（若有），用于了解项目需求全貌，监督项目推进与需求落地。
1.3 软件项目概述
本软件项目核心信息如下：
•项目名称：学院学生综合服务与党团管理平台
•用户单位：某高校信息学院（全院师生约1200人，其中学生约1100人、教职工约100人，覆盖各年级、各专业）
•开发单位：学院学生项目开发团队（由信息学院相关专业学生组成，接受学院指导老师监督）
•项目核心目标：针对当前学院学生事务管理中“党团流程审批繁琐、证明开具效率低、政策咨询分散、信息通知易遗漏”等痛点（现有模式高度依赖人工登记、微信群推送，存在沟通成本高、追溯困难、信息不统一等问题），打造“一站式”学生综合服务与党团管理窗口，助力学院学生工作数字化转型。
•核心功能及用途：涵盖党团流程管理、证明在线开具、政策智能咨询、精准通知推送等核心模块，实现师生事务办理电子化、政策咨询智能化、通知推送精准化、管理过程规范化，从而降低师生沟通成本，提升学院学生工作管理效率与服务质量。
1.4 文档概述
本文档围绕“学院学生综合服务与党团管理平台”的软件需求展开，整体遵循“总体概述—约束说明—详细需求—验收标准—原型参考”的逻辑结构，共分为五章，各章节核心内容及作用如下：
•第一章 引言：明确文档编写目的、读者对象、项目核心信息、文档结构，界定关键术语及参考资料，为全文提供总体框架与基础说明。
•第二章 一般性描述：阐述系统的运行环境（硬件、软件）、设计约束、接口约束及其他前置条件，为后续功能设计与开发提供约束依据。
•第三章 功能需求描述：作为文档核心章节，详细定义系统各大功能模块、用例场景、业务流程及输入输出要求，将用户业务需求转化为可执行的功能规格。
•第四章 非功能需求：明确系统的性能、安全、易用性、可扩展性等非功能指标，以及界面设计规范、交付标准与验收准则，保障软件质量与用户体验。
•第五章 软件原型概述：简要介绍系统的原型设计思路、涵盖的核心功能模块、使用的原型设计工具，为开发团队提供界面与交互的参考依据，辅助需求落地。
1.5 定义
•微人大：学校校级综合服务系统，主要用于全校师生的综合事务办理。本项目与微人大实行物理隔离，无直接接口对接，无法直接获取其后台数据，相关关联数据需通过手动录入方式同步。
•Kingbase（人大金仓数据库）：本项目指定使用的底层国产数据库系统，用于存储系统所有业务数据、用户信息及操作日志，保障数据存储的安全性与兼容性。
•分级审批：指系统中各类业务审批流程（如党团关系转接、评优评先申请、证明开具审批等），依据管理员权限层级（初级管理员→高级管理员→学院领导）逐级流转、审核的机制，确保审批流程规范、可追溯。
•一站式服务：指整合党团管理、证明开具、政策咨询、信息通知等各类学生事务，为师生提供“一站式”入口，实现事务办理“少跑腿、不跑腿”，提升服务效率。
•电子化办理：指将传统人工办理的学生事务（如证明开具、党团流程审批）转移至线上系统，实现申请、审核、办结全流程线上化，减少纸质材料，提升办理效率。

2. 软件的一般性描述
2.1 软件产品与其环境之间的关系
本系统是一个面向学院内部的综合服务平台，其与外部环境的关系具体表现如下：
（1）与外部用户的关系：系统的目标用户涵盖约1000余名终端学生用户和部分管理人员（包括辅导员、班主任、团委老师等） 。针对不同的使用场景，系统产品形态需同时支持移动端（方便学生随时随地进行高频的浏览与简单操作）与 PC 端（方便管理员基于大屏幕进行复杂表单的审批、数据统计与长文档处理） 。
（2）与其他软件系统的关系：
●校级系统隔离：本系统与校级“微人大”系统保持物理隔离，无法直接调用其 API 接口获取全校数据 。系统间的数据衔接主要依赖管理员手动进行具有标准格式的 Excel、Word、PDF 等文档的导出与批量导入 。
●外部信息抓取：对于外部新闻和通知的抓取，系统仅与学校公开官方网站（如人大新闻网）产生关联，不与具有强反爬虫机制的商业系统（如微信公众号服务器）进行直接的爬虫对接 。
(3)与硬件系统的关系：系统预期部署于学院提供的、配置有指定数据库环境的局域网/内  网服务器上 。
2.2限制与约束
在系统的设计、开发与运行过程中，需严格遵守以下限制与约束条件：
(1)底层数据库约束：系统后端的数据存储被强制要求采用国产人大金仓（Kingbase）数据库，开发框架必须解决与该数据库的兼容性适配问题 。
(2)数据安全与隐私约束：学生的身份证号、生源地、户籍地、导师信息、修学及延毕等历史记录被视为高敏感数据 。上述数据必须在数据库中严格保密存储，并从系统级限制访问权限，仅高级管理员可见，严禁向普通学生或三级以下权限人员公开 。
(3)架构与可维护性约束：系统必须采用模块化开发，代码结构须稳定清晰，严禁“补丁式”的劣质代码堆砌，以确保该平台在当前课程结束后，能够顺畅移交给下一届学生团队进行持续的迭代与维护 。
(4)UI 界面与视觉约束：系统的整体美术风格必须符合“严谨、正式、朴素”的设计规范，严禁采用过度活泼化、娱乐化的视觉元素，以契合学院党团事务及各项行政管理的严肃性要求 。
(5)通知渠道成本约束：由于短信发送需调用第三方服务并产生额外费用，平台的批量推 送功能应优先依赖小程序内消息、系统站内信或邮件 。短信功能在当前版本可仅作模拟记录处理 。
2.3假设与前提条件
本系统各项需求和功能的顺利实现，均建立在以下假设与前提条件之上：
(1)服务器与环境假设：假设学院能够协调金仓公司及相关领导，按时提供已配置好 Kingbase 运行环境的服务器供项目组进行部署与联调 。
(2)数据初始化假设：由于无法自动获取外部数据，假设在系统上线初期，学院相关老师能够梳理并上传初始的政策文档（PDF/Word）、初始题库，以及脱敏后的学生基础信息表，从而完成系统的冷启动 。
(3)用户身份标识假设：假设所有系统终端用户的学号均是唯一且真实的，系统内的身份验证、角色划分及数据流转均建立在以“学号”作为唯一标识的一对一绑定基础之上 。
(4)核心业务稳定性假设：假设诸如“入党申请、积极分子、发展对象”等党团发展事务的标准流程和时间线规范，在较长周期内保持高度稳定，不会发生频繁且重大的逻辑变更 。

3.2 软件需求的用例模型
●角色划分：
○一级角色（学院领导）：宏观数据查看。
○二级角色（管理老师）：：负责业务审批、数据上传及动态维护 。拥有敏感信息（如身份证号、修学/延毕记录）的查看权限 ，并可发布政策与精准推送通知 。
○三级角色（班团骨干/助教）：拥有部分管理权限，负责对接本班级/支部的基础事务，起到学生与学院间的桥梁作用 。注： 助教原则上不开放审批权限
○四级角色（普通学生）：身份绑定、发起申请、智能问答查询、查看个人画像、接收定向通知。
●核心用例自然语言描述：
○用例：发布政策与智能问答：老师登录PC端上传PDF/Word政策文件（<30MB），系统解析入库。学生在手机端输入问题，系统检索库内文件给出标准回答及文件下载链接。
○用例：发起与处理审批：学生填报申请表单提交，表单流转至班主任（初审），再流转至团委老师（终审）。老师如遇误操作，可在24小时内点击“撤回审批”并重新处理。

4. 其它软件需求描述
4.1 性能要求
并发处理能力：系统需承载学院约 1200 名师生的基础数据 。针对高峰期（如党团材料集中申报、奖学金评定）需求，系统设计需支持全量用户规模的并发使用 ，后端服务的峰值并发处理能力应能应对实际活跃访问需求 。
响应时间约束：
基础交互：静态页面加载与基础数据查询（如个人信息浏览）响应时间控制在 2 秒以内。
业务逻辑：智能问答模块由于涉及知识库检索与 AI 匹配，响应时长需控制在 3 秒以内 。
文件处理：对于 30MB 以内的证明文件下载或管理员批量导入导出，响应时长不超过 5 秒 。
4.2 设计约束
技术栈约束：
架构模式：采用前后端分离的网页版方案，弃用微信小程序架构以规避复杂的接口限制及反爬虫机制 。
后端：采用 Python Django 框架，利用其内建的权限管理功能 。
前端：确保同时兼顾手机端（处理高频任务）与电脑端（处理复杂任务）的访问体验 。
数据库：强制使用人大金仓 (Kingbase) 数据库 。
身份验证与账号逻辑：
认证体系：基于学号及基本信息进行实名验证 。系统需预置学生基础数据，支持 Excel 等文档的批量导入 。
权限分级：严格执行 4 个等级的权限划分，确保不同角色（领导、老师、骨干、学生）的操作边界 。
安全性要求：
敏感信息保护：身份证号、生源地、修学记录等核心隐私数据必须严格加密存储，且仅对二级（管理老师）及以上角色可见 。
操作审计：系统必须强制记录所有管理员的操作日志，以备溯源 。
通知渠道：优先支持邮件和微信提醒，短信功能仅做模拟记录以控制费用 。
4.3 界面要求
视觉规范：整体遵循“严谨、正式、朴素”的校园风格 。以“人大红”为主视觉色，提升品牌一致性。
布局与导航：
首页结构：采用直观的功能区域划分，清晰分发“智能问答（P0）”、“党团事务（P0）”等高频业务 。
管理端：侧重于数据表格的高效展示，支持一键筛选及批量审批操作，特别是针对荣誉展示与学生画像的管理 。
多端适配：通过响应式布局确保手机端与 PC 端的无缝切换，手机端侧重快捷查阅，PC 端侧重复杂数据的导入导出 。

结项节点：完成 P1 模块（学生画像、荣誉展示）开发及金仓数据库的服务器配置 。
